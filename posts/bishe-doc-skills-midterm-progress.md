bishe-doc-skills 今天升到了 0.2.0（提交 651c0cc）。除了把任务书从开题报告技能里拆出来，还新增了中期检查技能 `midterm-check`。技能数从 7 个变成 9 个。package.json 里的版本是 0.2.0，没有打 git tag，也没有发 GitHub Release。

我今天在 Node v24.22.1 下对着这个提交跑官方测试，校验是「9 个技能校验通过」，21 条安装器测试全绿；Actions 的 Node 18、20、22 也通过（run 45677137148）。技能正文和安装结果都是我在本地读文件、写到临时目录后核对的。各校中期检查表不一样，我没有用某一所学院的正式表格或真实中期答辩流程核对过。

## 先对照任务书，再写完成情况

`midterm-check` 一开头就把范围划清了：中期检查要对照任务书和开题进度如实汇报，已经完成什么、差在哪里、下一步怎么赶。不要把计划写成已经完成，也不要写成一篇新的开题报告。填写任务书请用 `task-book`，写开题请用 `thesis-proposal`。

建议结构里有一张进度对照表，栏目是「计划阶段 / 计划时间 / 计划工作 / 实际完成情况 / 是否按期 / 说明」。技能要求每一行都能在任务书或开题进度里找到依据；还没开始的阶段如实写「未开始」，不要提前打勾。若已经有项目代码，先用 `code-to-thesis` 提取真实模块，再去对照任务书，防止把「计划做」写成「已完成」。

其他几项同样具体。已完成工作按模块或章节写，没有的材料不要列。存在的问题每条都要有对应的解决或追赶办法，不要只写「正在努力」。如果要砍功能、改技术栈或延期，写清理由，并标明须经指导教师同意，不要擅自改题。阶段性成果里的截图必须来自真实系统；没有就写「待用户补充」，不要编造链接或数据。

## 红线和中期答辩

红线是：不代写指导教师评语、评分、是否同意继续的意见；未完成的工作不得写成已完成；没有实测的结果不得填写通过率或性能数据；不编造工作量、用户数、实验数据。学校要求中期答辩时，技能建议准备 5–8 分钟：题目与目标大约半分钟，已完成功能和演示要点 3–4 分钟，问题与下一步 1–2 分钟。演示脚本只写已经能跑的功能；现场环境不稳就建议提前录屏。可能被问到的是完成比例怎么算、未完成部分来不来得及、和任务书不一致的地方。

我在干净临时目录里跑过默认安装，一共写入 28 个文件（9 个技能各写到 `.claude/skills`、`.agents/skills`、`.trae/skills`，再加一份 `AGENTS.md`）。刚写出的 `midterm-check/SKILL.md` 三份内容相同，开头是：

```
---
name: midterm-check
description: "毕业设计中期检查材料（进度对照任务书、已完成工作、问题与风险、下阶段计划、成果清单）。写中期报告、填中期检查表、准备中期答辩时使用。"
---
# 毕业设计中期检查
```

这是本地写文件的结果，不能写成「客户端已经加载了这份技能」。这套技能帮你整理自己做的工作，不是代写工具，也要遵守学校关于 AI 辅助写作的规定。
