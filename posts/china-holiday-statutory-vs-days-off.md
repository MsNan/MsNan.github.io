我在 cn-dev-mcp 里写过一组节假日工具：`holiday_check` 判断某天上不上班，`workday_count` 数两个日期之间有几个工作日，`workday_add` 算"下单后第 3 个工作日是哪天"。数据是手抄的国务院办公厅放假通知，单元测试 13 条全绿，平时在 Cursor 里问"10 月 10 号要上班吗"也答得对。

今天想给 2027 年补一条用例，顺手搜了一下，发现 2027 年的放假通知（国办发明电〔2026〕10号）11 月 5 日就发了，而我的工具到现在还在每条结果里附一句"2027 年放假安排国务院办公厅尚未公布"。借这个机会把整块逻辑重新对了一遍，下面是对出来的 4 个问题。

## 数据长什么样

每年一条记录：放假区间、调休上班日，加上通知原文链接。

```ts
2026: {
  notice: '国务院办公厅关于2026年部分节假日安排的通知（国办发明电〔2025〕7号）',
  holidays: [
    { name: '元旦', start: '2026-01-01', end: '2026-01-03' },
    { name: '春节', start: '2026-02-15', end: '2026-02-23' },
    // ……
  ],
  workdays: ['2026-01-04', '2026-02-14', '2026-02-28', '2026-05-09', '2026-09-20', '2026-10-10'],
},
```

判断逻辑也很直接：在放假区间里就是"法定节假日"，在调休上班列表里就是"调休上班"，剩下的按周六日区分周末和工作日。

```ts
if (index.has(key)) return { ...base, type: '法定节假日', isWorkday: false, holiday: index.get(key) }
if (workSet.has(key)) return { ...base, type: '调休上班', isWorkday: true }
return weekend ? { ...base, type: '周末', isWorkday: false } : { ...base, type: '工作日', isWorkday: true }
```

复现脚本直接导入仓库编译后的 `dist/lib/holiday.js`，农历日期用仓库本来就依赖的 lunar-javascript 算，环境 Node 24。

## 1. 数据过期了，工具自己不知道

没有内置数据的年份，工具会退回"只按周末算"，并在 `note` 里提示。这个设计本身没问题，问题是"哪一年还没公布"是我 10 月中旬写死的：

```ts
// 2027 年安排截至 2026-10-16 尚未由国务院办公厅公布
export const PENDING_YEARS = [2027]
```

通知一发，这句话就成了错误信息。拿 2027 年的通知逐日对比：

```text
2027-02-08 周一  工具：工作日 isWorkday=true  | 实际：春节放假
2027-01-31 周日  工具：周末   isWorkday=false | 实际：调休上班
2027-06-09 周三  工具：工作日 isWorkday=true  | 实际：端午放假
2027 全年 isWorkday 判断错的天数：23
2027 年 2 月工作日：工具 20，实际 15
2027-02-04 下单 3 个工作日：工具 2027-02-09（周二），实际 2027-02-16（周二）
```

23 天是这么来的：7 个假期落在周一到周五的放假日 18 天，加上 5 个周末调休上班日。2027 年还有个特别的地方，端午（6 月 9 日）和中秋（9 月 15 日）都是周三，只放当天 1 天，不再凑 3 天小长假，政策解读里写的是"如逢周三则只在当日放假"。只按周末算，这两天一定会被当成工作日。

`note` 字段确实返回了，但调用方是大模型，它拿到 `isWorkday: true` 和一句备注，很可能只看前者。

回头看三年的发布日期：2025 年的通知是 2024-11-12 发的，2026 年的是 2025-11-04，2027 年的是 2026-11-05。规律很明显，每年 11 月上旬要补一次数据。我把这个日期写进了数据文件的注释，并把 `PENDING_YEARS` 改成 `[2028]`。

## 2. 放假 ≠ 法定节假日

这是改数据时才意识到的。我的工具把放假区间里的每一天都标成"法定节假日"，2026 年一共 33 天。但《全国年节及纪念日放假办法》（2024 年修订，2025 年起施行）第二条规定的全体公民放假节日只有 7 个、13 天：

- 元旦 1 天；春节 4 天（农历除夕、正月初一至初三）；清明 1 天（清明当日）
- 劳动节 2 天（5 月 1 日、2 日）；端午 1 天；中秋 1 天；国庆 3 天（10 月 1 日至 3 日）

剩下的 20 天是调休挪过来的，或者本来就是周末。逐日看：

```text
2026-02-15 周日 → type=法定节假日 holiday=春节   法定?否（腊月二十八，本来就是周日）
2026-02-16 周一 → type=法定节假日 holiday=春节   法定?是（除夕）
2026-04-05 周日 → type=法定节假日 holiday=清明节 法定?是
2026-04-06 周一 → type=法定节假日 holiday=清明节 法定?否（清明逢周日，周一补假）
2026-10-05 周一 → type=法定节假日 holiday=国庆节 法定?否（调休）
```

如果只是问"这天上不上班"，两者没区别。但做排班、算加班费就不一样了。《劳动法》第四十四条：休息日安排工作又不能安排补休的，支付不低于工资 200% 的报酬；法定休假日安排工作的，支付不低于 300%。人社部 2025 年的工资折算通知里，年工作日也是按"365 − 104 − 13 = 248 天"算的。把 10 月 5 日标成"法定节假日"，HR 系统照着算就会多付一倍。

改法是在数据里给每年加一个 `statutory` 数组，列出这 13 天，`dayInfo` 返回里加 `statutory: true/false`，放假区间里的非法定日改成 `type: '放假调休'`：

```ts
const base = { date: key, weekday: WEEK[wd], statutory: statutorySet.has(key), dataAvailable: !!HOLIDAYS[year], note: yearNote(year) }
if (index.has(key)) return { ...base, type: base.statutory ? '法定节假日' : '放假调休', isWorkday: false, holiday: index.get(key) }
```

`isWorkday` 不受影响，只是 `type` 多了一个取值。原来用 `type === '法定节假日'` 判断"是否放假"的调用方需要改成看 `isWorkday`，这一点得写进更新说明。

## 3. "第 N 个工作日"的几个边界

`addWorkdays` 的约定是"不含当天"：

```text
addWorkdays(2026-09-30 周三, 3)  → 2026-10-10 周六 type=调休上班
addWorkdays(2026-10-01 周四, 0)  → 2026-10-01 周四 type=法定节假日
addWorkdays(2026-10-01 周四, 1)  → 2026-10-08 周四
addWorkdays(2026-12-30 周三, 3)  → 2027-01-04 周一（原数据）/ 2027-01-05 周二（补上 2027 后）
```

几点说明：

- 9 月 30 日下单、3 个工作日内发货，算出来是 10 月 10 日周六。按国家调休这天确实上班，但如果你的仓库周六本来就不发货，这个答案就不对了。工具只能回答"按国家放假安排"，业务上要不要跳过周六，得调用方自己决定。补丁里我把这个口径写进了 `workday_add` 的工具描述。
- `n = 0` 原样返回输入日期，哪怕当天放假。我没改行为，只在注释里写清楚，免得有人拿它当"下一个工作日（含当天）"用。
- 跨年的情况最容易出事。12 月 30 日加 3 个工作日，旧数据没有 2027 年，把 1 月 1 日当成普通周五，算出 1 月 4 日；补上数据后是 1 月 5 日。跨年查询是最常见的，正好卡在数据最容易缺的地方。

## 4. 手抄的数据要能自己检查

两份通知加起来几十个日期，全靠手抄。这次补 2027 年数据之前，我先写了一个自检，每个内置年份检查四件事：

1. 调休上班日必须是周六或周日；
2. 调休上班日不能落在放假区间里；
3. 用 lunar-javascript 按放假办法算出 13 个法定日（除夕、清明节气、端午、中秋），它们必须都在放假区间里；
4. 统计全年最长连续上班天数。修订后的放假办法第七条要求"除个别特殊情形外，法定节假日假期前后连续工作一般不超过 6 天"。

```js
const cny = Lunar.fromYmd(+y, 1, 1).getSolar()
const expect = [`${y}-01-01`, cny.next(-1).toYmd(), cny.toYmd(), cny.next(1).toYmd(), cny.next(2).toYmd(),
  Lunar.fromYmd(+y, 1, 1).getJieQiTable()['清明'].toYmd(), `${y}-05-01`, `${y}-05-02`,
  Lunar.fromYmd(+y, 5, 5).getSolar().toYmd(), Lunar.fromYmd(+y, 8, 15).getSolar().toYmd(),
  `${y}-10-01`, `${y}-10-02`, `${y}-10-03`].sort()
assert.deepEqual([...d.statutory].sort(), expect)
```

结果：

```text
2025: 调休上班日不是周末 0；与放假重叠 0；法定日不在放假区间 0；全年最长连续上班 5 天
2026: 调休上班日不是周末 0；与放假重叠 0；法定日不在放假区间 0；全年最长连续上班 6 天（到 2026-01-09）
2027: 调休上班日不是周末 0；与放假重叠 0；法定日不在放假区间 0；全年最长连续上班 6 天（到 2027-02-19）
```

原来的数据没有抄错。这条测试真正的价值在以后：明年 11 月补 2028 年数据时，把某个调休日期抄错一天，它会直接报出来。`statutory` 数组也是手写的，同样有这条测试兜着。

## 改动汇总

- 补 2027 年数据（7 个放假区间、5 个调休上班日），`PENDING_YEARS` 改为 `[2028]`；
- 工具描述里的年份改成从数据生成，不再写死"2027 年尚未公布"；
- 每年加 `statutory`，`type` 区分"法定节假日"和"放假调休"，返回里加 `statutory` 字段；
- 加数据自检测试，原有 13 条测试加 1 条，共 14 条全部通过。

补丁还没合进仓库，`type` 多了一个取值，得先确认有没有调用方依赖旧值。

## 小结

- 节假日数据有"保质期"，每年 11 月上旬会变。代码里写死的"尚未公布"本身也是数据，也会过期。
- "放假"和"法定节假日"是两个概念：判断上不上班看放假安排，算 300% 加班费只看那 13 天。
- 年份没有数据时，退化到"只按周末算"并附一句备注，对人类读者够用，对大模型不太够。
- 手抄的日期要配一个能独立推算的自检，农历节日和节气用库算一遍，再跟通知对上。
