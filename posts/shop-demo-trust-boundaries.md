淘好物是我写的一个 uni-app 演示商城，前端加 Express 后端，方便把下单、支付、发货这条链路跑通。README 里写得很清楚：支付和发货都是模拟的，lowdb 只适合演示，正式环境要换数据库、接真实短信和支付。这周我把自己当成要把这套后端抄进项目的人，拿脚本对着接口打了一遍。仓库当前 HEAD 是 fcd00ee。下面的结果都是本地实测，用的 Node 24.22.1，没有接真实支付，也没有在生产环境和真机小程序上跑过。

以前写过购物车数量、售后状态机和短信登录，这几处今天不再展开。这次只看服务端对用户提交字段到底信到什么程度。

## 一、新增地址校验手机号，编辑却不校验

`POST /api/addresses` 会检查姓名、11 位手机号、地区和详细地址。手机号写成 `12345`，接口返回 400「请完整填写收货信息」，这是对的。

同一条已经建好的地址，改用 `PUT`，把手机号改成 `abc`、姓名改成空字符串：

```text
status 200
name: ""
phone: "abc"
region: "火星"
```

编辑接口把非法数据原样存进去了。原因在这一行：

```js
Object.assign(a, { ...req.body, id: a.id, uid: a.uid })
```

`PUT` 只保住了 `id` 和 `uid`，body 里其余字段都会写进地址对象。我又试着带上 `isAdmin: true` 和 `note: "injected"`，返回里这两个字段都在；`uid` 仍是我自己的，没被改成 99999。

这个脏地址可以直接拿去下单。订单里的收货信息是地址的一份快照，`phone` 仍是刚才写入的非法值，`isAdmin` 和 `note` 也被拷了进去。下单接口只确认「这个地址 ID 属于当前用户」，不会再验一次手机号和姓名。

前端编辑页其实有同样的手机号正则，正常点保存走不到这一步。但接口是开着的，脚本或改过的客户端可以直接打。页面上「设为默认」也会把整条地址对象再 PUT 回去，如果库里已经脏了，还会把脏数据再写一遍。

## 二、规格是前端拼的字符串，服务端不核对

种子数据里 20 件商品都有「颜色」和「规格」两组选项，比如经典黑 / 珍珠白，标准款 / 升级款。页面上选完之后用 ` / ` 拼成一串交给后台。这些规格没有单独的加价，服务端下单时用的是商品原价，这一点本身没问题。

问题是：这串规格完全由客户端说了算。下单时我传了 `256TB / 钻石限量版`——这件 T 恤根本没有这个规格，订单照样 200，明细里就写着这行字，价格还是原价 59。购物车加购走的也是同一套逻辑，不检查选项是否存在。

对演示数据来说，这只是订单上看起来很怪。如果以后给不同规格做了不同价格，还沿用现在这种写法，用户就能随便传一档规格、按基础价下单。

## 三、买家登录后，可以给自己的订单发货

付完模拟支付，订单变成「待发货」。这时用买家自己的 token 调 `POST /api/orders/:id/ship`，返回 200，状态变成「待收货」，时间线上写着「商家已发货（模拟）· 顺丰速运 SF1234567890」。再调确认收货，整单就是「已完成」。支付方式我写成「我随便写的支付方式」，也被原样存进了订单。

管理端另有一个发货接口，会要求运单号，没填是 400，填了才会改状态并记下快递信息。买家这边不用填运单号，也走不到管理端那套校验。

这条接口 README 里写了，订单页上也有「模拟发货」按钮，仓库里的 e2e 会点它。演示环境这样设计，是为了不依赖后台也能把流程走完，这一点我要说清楚：它不是偷偷留下的漏洞，是演示功能。如果直接抄到对真实用户开放的服务上，又不拆掉，就变成买家给自己点发货。

## 四、两处顺带踩到的问题

后台把某件商品的 `shop` 改成 `null` 之后（商品编辑并不强制填店铺名），搜索「T恤」还能返回：商品名先匹配到，后面的 `shop.includes` 被短路了，不会抛错。搜「旗舰」或一个谁的名字都不包含的词，接口直接 500，报 `TypeError: Cannot read properties of null (reading 'includes')`。搜索里对店铺名也没有像商品名那样做大小写折叠。

订单号是 `TB` 加上毫秒时间戳，再加一个 0 到 99 的随机数。我连打了几次并发下单，其中一次 24 毫秒内 30 个订单，有一个号 `TB179471005131027` 出现了两次。另外两次 30 单、40 单没有撞上。不是每次必现，但这个生成方式在同一毫秒里只有一百个格子，并发上去就会撞。

## 五、补丁怎么改

我在本地补了一版，还没合进仓库：编辑地址跟新增用同一套校验，而且只允许改姓名、手机号、地区、详细地址和默认标记，多余的键不会再写进去；下单前再验一次地址，规格必须是各组选项按页面同样方式拼出来的组合，加购也会做同样的检查；买家发货接口只在开发模式保留，生产环境返回 403「请通过管理后台发货」——我在 `NODE_ENV=production` 下测过，买家这边是 403，管理端带着运单号仍然可以发，开发模式里原来的「模拟发货」也还能用；搜索时对空的 `shop` 做了保护，并且统一按小写比；订单号改成再拼上自增序号，补丁后再并发 40 单，40 个号都不同，同一毫秒里的几单是靠序号分开的。支付方式也收成只接受支付宝、微信、银行卡，其它值回退到支付宝。

这只是演示项目，补丁也只在本地接口层验证过，没有改前端按钮的显示逻辑，没有在真机小程序和真实支付上跑。适合在抄代码之前先看一眼：哪些接口是演示用的，哪些用户输入还没在服务端收口。库存扣减、售后状态这些老问题，补丁里也没有一并处理。
